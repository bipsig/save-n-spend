# Insights Engine

This document describes the design of Highlights — ranked, plain-language
observations about a user's money, generated by deterministic rules rather than by
a language model.

Built. Two decisions moved between this design and the code, both because the
feature had to land without touching insights, bills or budgets — see
[Where it runs](#where-it-runs) for the endpoint and [The surface](#the-surface)
for the screen. Since then the rule set has grown from ten to fifteen and the
cards also appear on the dashboard and the Insights tab; the sections below
describe the code as it is.

## What it is

A short, ranked list of sentences that tell the user something true about their
money that they would otherwise have had to work out themselves:

> **Shopping will finish ₹2,300 over.** You're at ₹9,700 of ₹12,000 with 11 days
> left, spending ₹880 a day in it. Last month you finished ₹400 under.

> **Electricity is due in 3 days and your HDFC balance won't cover it.** The bill
> is ₹4,200; the account has ₹3,150.

> **You spent ₹3,400 less on Food & Dining than last month.** That's your biggest
> drop, and it's most of why your savings rate went from 8% to 19%.

Three properties make these worth building:

| Property | Why it matters |
|---|---|
| **Arithmetic the screens don't do** | The app shows a budget and a balance. It never divides remaining budget by remaining days, or compares a bill to the account it will be paid from. |
| **Joins across domains** | A bill, an account balance and a goal deadline live on three screens. The interesting sentences need two or three of them at once. |
| **Ranked, not exhaustive** | A chart shows everything equally. A highlight says *this is the one that matters this week*. |

## Why there is no LLM

Recorded so it is not re-litigated in six months.

An earlier revision of this document designed a chat assistant on Claude Haiku
with a fixed read-only tool set. It was rejected on **cost**, against a hard
product constraint that the app stays free to the user with no bill for the
operator either.

The numbers, at Haiku 4.5 rates ($1/MTok in, $5/MTok out):

| | |
|---|---|
| Per message (2 calls, tool round-trip) | ~6,000 tokens → **~$0.007**, about ₹0.60 |
| 50 users × 20 messages/month | ~$7/month |
| One user maxing a 30/day cap | ~$6/month, that user alone |

Cheap, but never zero, and linear in users. No provider offers a free API tier
for sustained production token usage, and a Claude Pro or Max subscription does
**not** cover API calls made by your own application — those are separate billing
systems.

**Important**
The LLM design's own central claim is what makes removing it cheap. It argued the
model "does not do the hard part — every number comes from an aggregation the API
already runs; the model picks which tool to call, then narrates the result." If
that is true, and it is, then the model was only ever doing two things: choosing
which of eight questions was being asked, and phrasing the answer. Rules choose by
firing conditions, and templates phrase. What is actually lost is the free-form
question box — the ability to answer a question nobody anticipated. That is a real
loss and this document does not pretend otherwise.

The eight read-only tools the assistant would have called map onto the same eight
data sources the rules read — spending totals, the category breakdown,
transactions, budgets, bills, goals, the health score and accounts. That analysis
was not wasted; only the model is gone.

## Where it runs

Server-side, as one endpoint:

```
GET /api/v1/highlights           →  { data: { highlights, generatedAt, timeZone, warmingUp? }, … }
GET /api/v1/highlights/history   →  paginated, newest first
```

Its own top-level route, not a child of `/insights` as this document first proposed.
Mounting it under `/insights` would have meant editing `insightsRoutes.ts` and the
insights controller, and the feature's constraint was that insights, bills and
budgets keep working exactly as they did. A separate route means the whole feature
is additive: `highlightRoutes.ts`, the snapshot and rules services and a
controller, plus one `router.use` line. Nothing existing changed to make room for
it.

Client-side was the tempting option, because `GET /insights` already returns most
of what the rules need and the app has it in hand — the rules could be a pure
function over a payload already in the query cache, with no new endpoint and no
latency.

It is server-side anyway, for one reason that outweighs that: **the copy and the
thresholds will need tuning after seeing real output.** A rule that fires too often,
or a sentence that reads badly, or a ₹500 floor that turns out to be ₹2,000, is a
one-line change. Server-side that ships in a deploy. Client-side it ships in an App
Store review, and the first month of this feature will involve several such
changes.

It also means the rules can later feed the [notification](architecture.md#notifications)
pipeline without being reimplemented, and that the engine is unit-testable in the
API workspace where a test runner will be easier to justify than in the app.

### It reuses the extraction P0a was already going to do

The rules need the same plain-signature services the assistant's tools needed, and
for the same reason: the aggregations currently live inside controllers welded to
`req`.

```ts
// transactionController.ts — args from req.query, identity from req.user,
// zone from a helper that itself takes a Request
const { startDate, endDate } = transactionSummaryQuerySchema.parse(req.query);
const match = { userId: new mongoose.Types.ObjectId(req.user!.userId), … };
const zone = await resolveZone(req);
```

So [P0a](#phasing) is unchanged from the assistant plan: move each aggregation into
its service with plain arguments, add `resolveZoneForUser(userId)`, leave the
controllers as thin parse-and-reply wrappers. `budgetService.budgetProgress` and
`healthService.healthScore` already have the right shape and need nothing.

**Note**
`GET /insights` already returns `trend`, `incomeVsExpense` (six periods), `byCategory`,
`byAccount`, `avgDailySpendCurrent`, `avgDailySpendPrevious`, `topCategory` and
`txnCount`. Most comparison rules need **no new aggregation at all** — the
current-versus-previous data and six periods of history are already computed. Read
that controller before writing a query.

## The rule contract

Every rule is a pure function from a snapshot to a highlight or nothing. No I/O, no
dates from `Date.now()`, no reading the database.

```ts
type Highlight = {
  ruleId: string;
  /** Stable per subject-and-month, so dismissing one doesn't hide the same
   *  rule's verdict about a different budget — or about this one next month. */
  key: string;
  severity: "urgent" | "warning" | "notice" | "win";
  title: string;                    // one line, number included
  body: string;                     // one or two sentences
  /** Paise at stake — the ranking signal. See below. */
  materiality: number;
  /** Where tapping it goes. */
  screen?: "budgets" | "bills" | "goals" | "health" | "activity" | "investments";
};

type Rule = {
  id: string;
  run: (snap: Snapshot) => Highlight | null;
};
```

The snapshot is assembled once per request and handed to every rule. It carries
plain facts, not documents:

```ts
type Snapshot = {
  currency: string;
  monthLabel: string;               // "YYYY-MM"
  daysElapsed: number;              // zone-local, including today; always >= 1
  daysInMonth: number;
  accounts: AccountFact[];
  budgets: BudgetFact[];            // this month, from budgetService
  prevBudgets: BudgetFact[];        // last month with its final spend
  bills: BillFact[];                // unsettled only, with zone-local daysUntilDue
  goals: GoalFact[];
  healthFocus: { label: string; hint: string } | null;   // from healthService
  thisMonth: { income: number; expense: number; byCategory: CategoryTotal[] };
  months: MonthTotals[];            // complete previous months, up to 3, oldest first
  categoryAverages: CategoryTotal[];
  currentStreak: number;            // consecutive days with a logged transaction
  investments: InvestmentFacts;
  recurring: RecurringFacts;        // repeating payments that are not bills yet
};
```

**Important**
There is no `now` on the snapshot: the calendar is already answered by the time a
rule runs. `daysElapsed` and `daysInMonth` are numbers the snapshot builder cut in
the user's zone, and every date-shaped fact (`daysUntilDue`, `monthsUntilDeadline`)
is a precomputed whole number. This is what makes the whole engine testable: a
fixture states "11 days left in the month" as numbers instead of depending on when
the suite runs. Never read the clock inside a rule.

Rules must also be **total** — a rule that assumes a budget exists, or that last
month has data, returns `null` instead of throwing. A single bad rule must not take
down the endpoint; the runner also catches per rule and logs, so one throw costs one
insight rather than the whole list.

## The rules

Fifteen rules: the ten the first version shipped with, then five added later (the
logging streak, three about investments, and recurring payments). Every threshold
pairs a **ratio** with an **absolute floor**, for reasons in
[noise control](#ranking-and-noise-control).

| Rule | Fires when | Says |
|---|---|---|
| `budget_pace` | Projected month-end spend exceeds the limit by ≥ ₹200, and ≥ 7 days elapsed | "Shopping will finish ₹2,300 over — ₹880/day with 11 days left" |
| `budget_comfortable` | Projected to finish ≥ 15% under, on a budget that was breached last month | "Groceries is on track to come in ₹1,900 under, after going over in August" |
| `bill_vs_balance` | An unpaid bill due ≤ 7 days exceeds the balance of any single account | "Electricity is ₹4,200 and due Thursday; HDFC has ₹3,150" |
| `bill_cluster` | ≥ 3 bills, or ≥ 25% of monthly income in bills, due in the same 7 days | "₹18,400 of bills land between the 12th and the 18th" |
| `category_spike` | A parent category is ≥ 40% above its 3-month average, delta ≥ ₹500 | "Transportation is ₹1,600 above its usual ₹4,000" |
| `category_drop` | Same, downward — a win, not a warning | "Food & Dining is ₹3,400 below your average" |
| `savings_rate_move` | Savings rate moved ≥ 5 percentage points versus last month | "Your savings rate went from 8% to 19%" |
| `goal_pace` | At the trailing 3-month contribution rate, a goal misses its target date | "The laptop fund lands in March, two months after your June target" |
| `health_focus` | `healthScore().focus` is present | Surfaces that pillar's existing `hint` verbatim |
| `catch_all_heavy` | ≥ 30% of the month's expense, and ≥ ₹2,000 of it, sits in one catch-all category (Others, Misc, Uncategorised…) | "38% of your spending is in Others, so the breakdown can't tell you much" |
| `logging_streak` | Logged something on ≥ 3 days in a row; keyed by milestone (3, 7, 14, 30, 60, 90, 180, 365) so a dismissal holds across the days inside one bucket | "12 days in a row logging transactions" |
| `investment_stale` | Holdings exist, a value update is on record, and the newest is ≥ 35 days old; keyed per month | "Your investment values are about 6 weeks old" |
| `investment_milestone` | Portfolio value is at or past a round number (₹5k up to ₹10L); fires once per bucket | "Your investments crossed ₹1,00,000" |
| `investing_streak` | Contributed to investments in ≥ 3 months in a row; keyed by milestone (3, 6, 12, 24, 36, 60) | "6 months of investing in a row" |
| `recurring_found` | The recurring-payment detector has suggestions that are not bills yet; keyed by the set of suggestions | "Rent looks like a monthly payment" |

The five later rules all have materiality 0 except `recurring_found`, which is
ranked by a year of the suggestions' cost. Streaks, milestones and the stale-value
nudge are not money at risk, so they rank below anything with rupees on the line
and surface only on a quiet day.

Trip spending is split in the snapshot: the month's income, expense and
savings-rate totals include trip rows, but the per-category figures behind
`budget_pace`, `category_spike`, `category_drop` and `catch_all_heavy` leave them
out, because a holiday's food is not an everyday Food spike. Budgets come from
`budgetProgress`, which also excludes them.

`bill_vs_balance` compares against *individual* account balances, not their sum,
because money in a savings account is not going to pay a card bill on Thursday. It
is deliberately the highest-severity rule in the set: it is the only one that
predicts a payment actually failing.

**Important**
`health_focus` writes no copy of its own. `healthScore()` already selects the
weakest pillar below its `PAR` of 65, breaks ties toward the heavier weight, and
attaches a `hint` written for the user — so the rule reads `health.focus` and
passes the hint straight through. Re-deriving "the weakest pillar" here would give
the app two answers to that question, and the
[health detail screen](architecture.md#health-score) already shows the other one.

Rules 5 and 6 both read the same three-month average and differ only in sign. They
are separate rules rather than one signed rule so that their copy, severity and
floors can diverge — a ₹500 overspend deserves different words from a ₹500 saving.

## Division of labour with notifications

The app already pushes budget alerts at **80%** and **100%** of a limit
(`budgetAlertService`, event-driven, deduped per budget-month), and bill reminders
on a schedule. Highlights must not restate those.

| Concern | Notifications | Highlights |
|---|---|---|
| Trigger | An event crossed a threshold | The user opened the screen |
| Timing | Immediate, once per budget-month | On demand, recomputed each time |
| Content | *That* something happened | *Pace, projection, comparison, and joins* |
| Example | "You've used 80% of Shopping" | "At ₹880/day Shopping finishes ₹2,300 over" |

**Important**
No highlight may fire on "you crossed 80%" or "you went over" alone. The push
already said that, and repeating it is how a feature teaches users to ignore it.
`budget_pace` is allowed to fire *before* 80% is reached, and that is the point —
it is a projection, not a threshold.

## Ranking and noise control

This is where a rules engine actually succeeds or fails. Rules are easy; a list
that stays worth reading in month three is not.

**Rank by rupees, not by rule order.** Every insight carries `materiality` in
paise — the amount at stake — and the list sorts on it descending, with `severity`
as the tiebreak. A ₹4,200 bill that will bounce outranks a ₹300 category wobble
without anyone hand-ordering the rules.

**Show at most four.** Beyond that it is a report, not a highlight, and the ranking
stops mattering because everything is on screen anyway. Ties on materiality fall
back to severity in the order urgent, warning, win, notice. `rankHighlightRules`
returns every highlight that fired; `runHighlightRules` is that list capped at four.

**Every ratio needs an absolute floor.** A category that went from ₹60 to ₹180 is
up 200% and is not news. The floors in the table above exist for exactly this; a
percentage without a rupee floor is the single most common way this kind of feature
becomes noise.

**Dedupe on `key`, cool down on dismissal.** `key` is stable per subject — rule id
plus budget/bill/goal id plus month — so the same insight about the same budget is
one insight, not one per visit. Dismissal lives on the phone, not the server:
`lib/highlights.ts` stores `key → time` under `sns.dismissedHighlights` and filters
the response. A dismissed highlight stays hidden for 7 days, or until its `key`
changes at the month boundary.

**Everything that fired is also recorded.** Each request writes every ranked
highlight, not just the four shown, to `HighlightLog`: one row per distinct `key`,
inserted once at first occurrence (`$setOnInsert` upsert) and never edited or
removed, whatever the live view later does. `GET /highlights/history` pages it,
newest first. A failed write is logged and never fails the request.

**Say nothing rather than something weak.** An empty list is a valid, good response:
*"Nothing needs your attention — spending is tracking where it did last month."*
Padding a thin list with observations nobody needed is what trains users to stop
reading. There is no minimum count.

## Cold start

The rules divide by history, and a new account has none. Comparison rules produce
nonsense or a divide-by-zero on a two-week-old account.

Gate the whole endpoint:

| Condition | Behaviour |
|---|---|
| < 14 days since the first transaction | Skip the snapshot; return a `warmingUp` message string with at most the logging streak |
| < 10 expense transactions | Same |
| Any rule needing month-over-month, with no complete previous month | That rule returns `null`; others still run |

The gate runs before the snapshot is built, so a warming account costs three cheap
queries. The **logging streak is exempt**: it is as true on day 3 as on day 300, and
this gate would otherwise hide it for two weeks. The response is `{ highlights,
generatedAt, timeZone, warmingUp }`, where `warmingUp` is the sentence to show, not
a reason code.

The screen shows an honest waiting state rather than an empty one — *"A few more
weeks of transactions and this gets useful."* The
[cold-start gate](architecture.md#cold-start-gate) is a separate concern: that one
is about the API being asleep.

## Testing

**This is the first thing in this repository that is straightforward to test, and it
is the first thing that is tested** — `src/services/highlightRules.test.ts` was the
repo's first test file, and `highlightSnapshotMath.test.ts` is now beside it. Both run
as part of `npm test --workspace=apps/api`, which also covers the other pure modules
(see [the developer guide](README.md#verify-a-change)).

It uses `node:test` and `node:assert/strict`: both are in the standard library, so
the suite added **zero dependencies**. On a free-tier deploy that matters more than
the nicer matchers a framework would give — and `tsconfig.build.json` keeps test
files out of `dist/`, so nothing test-related ships to Render.

Every rule is a pure function from a fixture to an expected insight. No database, no
network, no clock, no Express. A test is a snapshot literal and an assertion:

```ts
it("projects month-to-date spend to a month-end overrun", () => {
  const hit = byRule(runHighlightRules(snap({ budgets })), "budget_pace");
  assert.equal(hit.materiality, 740_000); // 970000/15*30 − 1200000
  assert.ok(hit.title.includes("7,400"));
});
```

Note what the fixture does *not* contain: a date. `daysElapsed: 15, daysInMonth: 30`
is stated as numbers, which is what makes the suite give the same answer at 11pm on
the 31st as it does at noon on the 1st. Every calendar question is answered by the
snapshot builder, which is the half that is not tested here.

What the tests are actually for, beyond correctness: they pin the **copy** and the
**thresholds**. Both will be tuned repeatedly, and a table of fixtures is how you
change a floor from ₹500 to ₹2,000 and immediately see which sentences stop firing.

Covered today, 31 tests over 13 suites (the five later rules included): a month with zero income (the divide-by-zero
in savings rate), a goal with no contributions, a goal with no deadline, a category
whose usual month is too small to be news, the first-week gate on both pace rules,
every rupee floor, the ranking order, and the cap at four.

### The snapshot half

The gaps this section used to list were all in the snapshot builder — the half that
touches Mongo and the calendar. Most of them were not really about Mongo: they were
about arithmetic that happened to be written next to a query.

So the arithmetic moved. `highlightSnapshotMath.ts` holds the calendar window and the
category rollup as pure functions of their arguments; `highlightSnapshotService.ts`
keeps the queries and hands rows over. The seam is drawn at **rows in, facts out**
rather than at the Mongo boundary, because the aggregation's shape is the easy part to
get right and the calendar is not.

`highlightSnapshotMath.test.ts` covers it in 29 cases across six groups:

| Group | What it pins |
|---|---|
| `snapshotWindow` — the month | That the month comes from the user's zone, not UTC (00:30 on 1 October in Delhi is still 30 September in UTC); that `daysElapsed` is `1` on the 1st and counts calendar dates rather than elapsed hours; February in a leap year; **31 days in a month containing a 23-hour day** (New York, March) — dividing hours by 24 would make that 30.96 and skew every pace projection in the month. |
| `snapshotWindow` — the comparison | That the current month is never one of its own comparison months; the **January year-cross**, where string arithmetic on `"YYYY-MM"` would produce `"2026--2"`; and that `windowStart` and `completeLabels` agree, so spend is never fetched and then silently dropped. |
| `snapshotWindow` — the divisor | That an account opened this month averages over one month, not three — dividing its non-existent history by three would tell the user every category had collapsed; that the divisor grows with the history up to the cap; and that it is never zero. |
| `categoryRoller` | Child under parent, top-level as itself, uncategorised as its own slice, and a **since-deleted** category named rather than printed as a hex string. |
| `rollUpFlows` | That a **backdated transaction lands in the closed month it belongs to** and not in this one; that a row outside the window is dropped rather than counted somewhere approximate; that averages divide by `monthsAveraged`; that a month before the account existed is **absent rather than zero** while a genuinely empty month inside the history *is* zero; that siblings sum on both sides of a comparison; and that every figure stays a whole number of paise. |
| `contributionStreak` | Consecutive months with at least one investment contribution, ending this month or last month when this month's has not landed yet. |

The absent-versus-zero distinction is the one worth restating: a zero-income month is
a real answer the savings-rate rule will act on, so "we have no idea" has to look
different from "you earned nothing".

**What is still not tested.** One thing, and it needs a database rather than a
fixture: `budgetProgress`. A budget created on the 20th is compared against spend from
the **1st**, because a budget is *for* a month and that is also what the Budget screen
shows — `daysElapsed` is unaffected either way, since it counts from the 1st
regardless. That is the intended reading, now written down; pinning it requires a Mongo
harness, which is the next thing to add here if the behaviour is ever in doubt.

## The surface

**Highlights is its own screen at `/assistant`**, reached from the hero row at the
top of the More tab — the row that used to promise an AI Assistant, now relabelled
"Highlights · What your money is doing this month". The screen shows the live list,
a warming-up state when the API sends `warmingUp`, and below it the permanent
history from `GET /highlights/history`, paged.

The same `useHighlights()` hook feeds two more places:

| Where | What it shows |
|---|---|
| Dashboard (`app/(tabs)/index.tsx`) | The single worst warning and the single best win off the top of the list; nothing is re-derived. |
| Insights tab (`app/(tabs)/insights.tsx`) | The ranked, dismissible cards, as this document first proposed. |

So the earlier decision to keep Insights untouched has since been reversed; the
reasons for the separate screen still hold — a highlight rule that throws cannot
take the charts down with it, and the cold-start gate does not have to reason about
a screen that has its own empty states. Because `useHighlights()` is a standalone
hook over a standalone endpoint and neither knows which screen renders it, adding a
surface was a presentational change.

The existing `assistant.tsx` was rewritten rather than deleted, so the route, the
More-tab hero and its gradient treatment all survive.

Card anatomy: severity icon and chip, one-line title carrying the number, one or two
sentences of body, a dismiss affordance, and the whole card as a tap target that
deep-links to the screen where something can be done about it. A highlight that names
a problem and doesn't offer the door to fix it is half a feature.

**Note**
The rule copy is generated server-side with the amounts already formatted into the
sentence, which means it is **not localised** and it **cannot be masked by privacy
mode** — unlike every other amount in the app, which renders through the client's
`formatAmount`. That is the deliberate cost of server-side copy, and it holds wherever the
cards appear: the Highlights screen, the dashboard and Insights all show real
amounts with privacy mode on. Keep sentences short
and put the number in the title where the existing typography can carry it.

From 2.8.4 the server's `formatAmount` and `formatPercent` (`apps/api/src/utils/money.ts`)
follow the app's rules: exact paise, one decimal on a measured percentage, and the
true minus (`₹9,500.00`, `37.5%`, `−5.1%`). See
[Server-written sentences](api-reference.md#server-written-sentences).

## Out of scope

| Not building | Why |
|---|---|
| Any write, edit or delete | Highlights observe; the screens are where things change |
| An LLM, in any form | [Why there is no LLM](#why-there-is-no-llm) |
| Free-form question answering | The acknowledged loss from dropping the model — a rules engine cannot answer what it was not written to answer |
| Push notifications for highlights | The existing rule-based alerts already cover the time-critical cases; a second push channel competing with them is how both get muted. (The recurring-payments find has its own notification, `recurringFound`, raised by the reminder job — separate from the highlight.) |
| Investment or product advice | A regulatory line, not a technical one — highlights describe the user's own data and arithmetic on it, and do not advise |

## Phasing

| Phase | Scope | Status |
|---|---|---|
| P0a | Extract the aggregations into plain-signature services; add `resolveZoneForUser`; no new feature | **Skipped** |
| P0b | Snapshot assembly, the rule runner, ranking, the cold-start gate, and the first test fixtures | Done |
| P0c | The ten rules, each with tests | Done |
| P0d | The Highlights screen | Done |
| Later | Logging streak, three investment rules and `recurring_found`; dismissal on the phone; the permanent `HighlightLog` history; the cards on the dashboard and Insights | Done |

P0b before P0c on purpose: the runner, the ranking and the noise controls are the
parts that decide whether this feature is good, and writing ten rules against a
runner that cannot rank or dedupe them produces ten rules that all need rewriting.
That held up — the ranking and the floors were tuned against fixtures before any
rule copy was final.

**P0a was skipped, deliberately.** It is a refactor of `insightsController`,
`transactionController` and `billController`, and the constraint on this feature was
that those keep behaving exactly as they did. A refactor that touches three
controllers to save duplication in a fourth is not a trade worth making against a
"change nothing else" requirement, so the snapshot service runs its own `$facet`
aggregation instead and reuses only what already had a plain signature:
`budgetProgress`, `healthScore`, and `billService`'s settlement helpers.

The cost is one duplicated aggregation shape: the month totals and the per-category
expense rollup now exist in both `insightsController` and
`highlightSnapshotService` (which, unlike the Insights breakdown, leaves trip spending
out of the per-category figures instead of folding it into a Trips slice). The rollup key is `parent ?? _id` in both places, which
is the invariant that actually matters — if those two ever disagree, the highlights
and the charts will name different categories, and P0a becomes worth doing after all.
That is the trigger to revisit it, not general tidiness.
