# Insights Engine

This document describes the design of Highlights — ranked, plain-language
observations about a user's money, generated by deterministic rules rather than by
a language model. Nothing here is built yet: `apps/mobile/app/assistant.tsx` is
still a `ComingSoon` placeholder.

## What it is

A short, ranked list of sentences that tell the user something true about their
money that they would otherwise have had to work out themselves:

> **Shopping will finish ₹2,300 over.** You're at ₹9,700 of ₹12,000 with 11 days
> left, spending ₹880 a day in it. Last month you finished ₹400 under.

> **Electricity is due in 3 days and your HDFC balance won't cover it.** The bill
> is ₹4,200; the account has ₹3,150.

> **You spent ₹3,400 less on Food & Dining than last month.** That's your biggest
> drop, and it's most of why your savings rate went from 8% to 19%.

Three properties make these worth building:

| Property | Why it matters |
|---|---|
| **Arithmetic the screens don't do** | The app shows a budget and a balance. It never divides remaining budget by remaining days, or compares a bill to the account it will be paid from. |
| **Joins across domains** | A bill, an account balance and a goal deadline live on three screens. The interesting sentences need two or three of them at once. |
| **Ranked, not exhaustive** | A chart shows everything equally. A highlight says *this is the one that matters this week*. |

## Why there is no LLM

Recorded so it is not re-litigated in six months.

An earlier revision of this document designed a chat assistant on Claude Haiku
with a fixed read-only tool set. It was rejected on **cost**, against a hard
product constraint that the app stays free to the user with no bill for the
operator either.

The numbers, at Haiku 4.5 rates ($1/MTok in, $5/MTok out):

| | |
|---|---|
| Per message (2 calls, tool round-trip) | ~6,000 tokens → **~$0.007**, about ₹0.60 |
| 50 users × 20 messages/month | ~$7/month |
| One user maxing a 30/day cap | ~$6/month, that user alone |

Cheap, but never zero, and linear in users. No provider offers a free API tier
for sustained production token usage, and a Claude Pro or Max subscription does
**not** cover API calls made by your own application — those are separate billing
systems.

**Important**
The LLM design's own central claim is what makes removing it cheap. It argued the
model "does not do the hard part — every number comes from an aggregation the API
already runs; the model picks which tool to call, then narrates the result." If
that is true, and it is, then the model was only ever doing two things: choosing
which of eight questions was being asked, and phrasing the answer. Rules choose by
firing conditions, and templates phrase. What is actually lost is the free-form
question box — the ability to answer a question nobody anticipated. That is a real
loss and this document does not pretend otherwise.

The eight read-only tools the assistant would have called map onto the same eight
data sources the rules read — spending totals, the category breakdown,
transactions, budgets, bills, goals, the health score and accounts. That analysis
was not wasted; only the model is gone.

## Where it runs

Server-side, as one endpoint:

```
GET /api/v1/insights/highlights   →  { data: { highlights, generatedAt, timeZone }, … }
```

Client-side was the tempting option, because `GET /insights` already returns most
of what the rules need and the app has it in hand — the rules could be a pure
function over a payload already in the query cache, with no new endpoint and no
latency.

It is server-side anyway, for one reason that outweighs that: **the copy and the
thresholds will need tuning after seeing real output.** A rule that fires too often,
or a sentence that reads badly, or a ₹500 floor that turns out to be ₹2,000, is a
one-line change. Server-side that ships in a deploy. Client-side it ships in an App
Store review, and the first month of this feature will involve several such
changes.

It also means the rules can later feed the [notification](architecture.md#notifications)
pipeline without being reimplemented, and that the engine is unit-testable in the
API workspace where a test runner will be easier to justify than in the app.

### It reuses the extraction P0a was already going to do

The rules need the same plain-signature services the assistant's tools needed, and
for the same reason: the aggregations currently live inside controllers welded to
`req`.

```ts
// transactionController.ts — args from req.query, identity from req.user,
// zone from a helper that itself takes a Request
const { startDate, endDate } = transactionSummaryQuerySchema.parse(req.query);
const match = { userId: new mongoose.Types.ObjectId(req.user!.userId), … };
const zone = await resolveZone(req);
```

So [P0a](#phasing) is unchanged from the assistant plan: move each aggregation into
its service with plain arguments, add `resolveZoneForUser(userId)`, leave the
controllers as thin parse-and-reply wrappers. `budgetService.budgetProgress` and
`healthService.healthScore` already have the right shape and need nothing.

**Note**
`GET /insights` already returns `trend`, `incomeVsExpense` (six periods), `byCategory`,
`byAccount`, `avgDailySpendCurrent`, `avgDailySpendPrevious`, `topCategory` and
`txnCount`. Most comparison rules need **no new aggregation at all** — the
current-versus-previous data and six periods of history are already computed. Read
that controller before writing a query.

## The rule contract

Every rule is a pure function from a snapshot to an insight or nothing. No I/O, no
dates from `Date.now()`, no reading the database.

```ts
type Insight = {
  ruleId: string;
  /** Stable per subject, so the same insight about the same budget dedupes. */
  key: string;
  severity: "urgent" | "warning" | "notice" | "win";
  title: string;                    // one line, already formatted
  body: string;                     // one or two sentences
  /** Paise at stake — the ranking signal. See below. */
  materiality: number;
  /** Where tapping it goes, e.g. { screen: "budgets", id } */
  link?: InsightLink;
};

type Rule = {
  id: string;
  run: (snap: Snapshot) => Insight | null;
};
```

The snapshot is assembled once per request and handed to every rule:

```ts
type Snapshot = {
  now: Date;                        // injected, never read from the clock
  zone: string;                     // the account's IANA zone
  currency: string;
  daysElapsed: number;              // in the current month, in `zone`
  daysRemaining: number;
  accounts: Account[];
  categories: Category[];           // the two-level tree
  budgets: BudgetProgressItem[];    // from budgetService
  bills: Bill[];
  goals: Goal[];
  health: HealthScore;              // from healthService
  thisMonth: PeriodTotals;
  lastMonth: PeriodTotals;
  history: PeriodTotals[];          // six months, oldest first
};
```

**Important**
`now` is a field on the snapshot, not a call to `new Date()` inside a rule. This is
what makes the whole engine testable: a fixture pins the date, and "11 days left in
the month" is deterministic instead of depending on when the suite runs. Never read
the clock inside a rule.

Rules must also be **total** — a rule that assumes a budget exists, or that last
month has data, returns `null` instead of throwing. A single bad rule must not take
down the endpoint; the runner also catches per rule and logs, so one throw costs one
insight rather than the whole list.

## The rules

Ten rules for v1. Every threshold pairs a **ratio** with an **absolute floor**, for
reasons in [noise control](#ranking-and-noise-control).

| Rule | Fires when | Says |
|---|---|---|
| `budget_pace` | Projected month-end spend exceeds the limit by ≥ ₹200, and ≥ 7 days elapsed | "Shopping will finish ₹2,300 over — ₹880/day with 11 days left" |
| `budget_comfortable` | Projected to finish ≥ 15% under, on a budget that was breached last month | "Groceries is on track to come in ₹1,900 under, after going over in August" |
| `bill_vs_balance` | An unpaid bill due ≤ 7 days exceeds the balance of any single account | "Electricity is ₹4,200 and due Thursday; HDFC has ₹3,150" |
| `bill_cluster` | ≥ 3 bills, or ≥ 25% of monthly income in bills, due in the same 7 days | "₹18,400 of bills land between the 12th and the 18th" |
| `category_spike` | A parent category is ≥ 40% above its 3-month average, delta ≥ ₹500 | "Transportation is ₹1,600 above its usual ₹4,000" |
| `category_drop` | Same, downward — a win, not a warning | "Food & Dining is ₹3,400 below your average" |
| `savings_rate_move` | Savings rate moved ≥ 5 percentage points versus last month | "Your savings rate went from 8% to 19%" |
| `goal_pace` | At the trailing 3-month contribution rate, a goal misses its target date | "The laptop fund lands in March, two months after your June target" |
| `health_focus` | `healthScore().focus` is present | Surfaces that pillar's existing `hint` verbatim |
| `catch_all_heavy` | ≥ 30% of the month's expense sits in one catch-all category | "38% of your spending is in Others, so the breakdown can't tell you much" |

`bill_vs_balance` compares against *individual* account balances, not their sum,
because money in a savings account is not going to pay a card bill on Thursday. It
is deliberately the highest-severity rule in the set: it is the only one that
predicts a payment actually failing.

**Important**
`health_focus` writes no copy of its own. `healthScore()` already selects the
weakest pillar below its `PAR` of 65, breaks ties toward the heavier weight, and
attaches a `hint` written for the user — so the rule reads `health.focus` and
passes the hint straight through. Re-deriving "the weakest pillar" here would give
the app two answers to that question, and the
[health detail screen](architecture.md#health-score) already shows the other one.

Rules 5 and 6 both read the same three-month average and differ only in sign. They
are separate rules rather than one signed rule so that their copy, severity and
floors can diverge — a ₹500 overspend deserves different words from a ₹500 saving.

## Division of labour with notifications

The app already pushes budget alerts at **80%** and **100%** of a limit
(`budgetAlertService`, event-driven, deduped per budget-month), and bill reminders
on a schedule. Highlights must not restate those.

| Concern | Notifications | Highlights |
|---|---|---|
| Trigger | An event crossed a threshold | The user opened the screen |
| Timing | Immediate, once per budget-month | On demand, recomputed each time |
| Content | *That* something happened | *Pace, projection, comparison, and joins* |
| Example | "You've used 80% of Shopping" | "At ₹880/day Shopping finishes ₹2,300 over" |

**Important**
No highlight may fire on "you crossed 80%" or "you went over" alone. The push
already said that, and repeating it is how a feature teaches users to ignore it.
`budget_pace` is allowed to fire *before* 80% is reached, and that is the point —
it is a projection, not a threshold.

## Ranking and noise control

This is where a rules engine actually succeeds or fails. Rules are easy; a list
that stays worth reading in month three is not.

**Rank by rupees, not by rule order.** Every insight carries `materiality` in
paise — the amount at stake — and the list sorts on it descending, with `severity`
as the tiebreak. A ₹4,200 bill that will bounce outranks a ₹300 category wobble
without anyone hand-ordering the rules.

**Show at most four.** Beyond that it is a report, not a highlight, and the ranking
stops mattering because everything is on screen anyway.

**Every ratio needs an absolute floor.** A category that went from ₹60 to ₹180 is
up 200% and is not news. The floors in the table above exist for exactly this; a
percentage without a rupee floor is the single most common way this kind of feature
becomes noise.

**Dedupe on `key`, cool down on dismissal.** `key` is stable per subject — rule id
plus budget/bill/goal id plus month — so the same insight about the same budget is
one insight, not one per visit. A dismissed insight stays suppressed for 7 days, or
until its `key` changes at the month boundary.

**Say nothing rather than something weak.** An empty list is a valid, good response:
*"Nothing needs your attention — spending is tracking where it did last month."*
Padding a thin list with observations nobody needed is what trains users to stop
reading. There is no minimum count.

## Cold start

The rules divide by history, and a new account has none. Comparison rules produce
nonsense or a divide-by-zero on a two-week-old account.

Gate the whole endpoint:

| Condition | Behaviour |
|---|---|
| < 14 days since the first transaction | Return an empty list with a `reason` of `"warming_up"` |
| < 10 expense transactions | Same |
| Any rule needing month-over-month, with no complete previous month | That rule returns `null`; others still run |

The screen shows an honest waiting state rather than an empty one — *"A few more
weeks of transactions and this gets useful."* The
[cold-start gate](architecture.md#cold-start-gate) is a separate concern: that one
is about the API being asleep.

## Testing

**This is the first thing in this repository that is straightforward to test, and
it should be the first thing that is tested.** The repo has no test suite today.

Every rule is a pure function from a fixture to an expected insight. No database, no
network, no clock, no Express. A test is a snapshot literal and an assertion:

```ts
it("projects a budget overrun from the current daily rate", () => {
  const snap = snapshot({ now: "2026-09-12", budgets: [shopping({ limit: 1_200_000, spent: 970_000 })] });
  expect(budgetPace.run(snap)?.title).toBe("Shopping will finish ₹2,300 over");
});
```

What the tests are actually for, beyond correctness: they pin the **copy** and the
**thresholds**. Both will be tuned repeatedly, and a table of fixtures is how you
change a floor from ₹500 to ₹2,000 and immediately see which sentences stop firing.

Cases worth fixtures on day one: a month with zero income (divide-by-zero in savings
rate), a budget created mid-month, a backdated transaction landing in a closed month,
a goal with no contributions at all, a category whose only history is this month, and
the 1st of the month with `daysElapsed = 1`.

## The surface

**Highlights become the top section of the existing Insights tab**, above the charts
that are already there. The charts answer "what happened"; the highlights answer "so
what". Putting them on one screen means the sentence and the chart backing it are a
scroll apart.

The **AI Assistant tab is retired** — `apps/mobile/app/assistant.tsx` and its route
are deleted rather than left as a `ComingSoon` for something that is no longer
planned. A permanent "coming soon" tab is worse than one fewer tab.

Card anatomy: severity accent, one-line title carrying the number, one or two
sentences of body, and a tap target that deep-links to the screen where something
can be done about it (`budgets`, a bill, a goal, the category's filtered Activity
view). A highlight that names a problem and doesn't offer the door to fix it is
half a feature.

Amounts render through `formatAmount` and respect privacy mode like every other
amount in the app.

**Note**
The rule copy is generated server-side, which means it is **not localised** and it
is not masked. Keep sentences short and put the number in the title where the
existing typography can carry it.

## Out of scope

| Not building | Why |
|---|---|
| Any write, edit or delete | Highlights observe; the screens are where things change |
| An LLM, in any form | [Why there is no LLM](#why-there-is-no-llm) |
| Free-form question answering | The acknowledged loss from dropping the model — a rules engine cannot answer what it was not written to answer |
| Push notifications for highlights | The existing rule-based alerts already cover the time-critical cases; a second push channel competing with them is how both get muted |
| Investment or product advice | A regulatory line, not a technical one — highlights describe the user's own data and arithmetic on it, and do not advise |

## Phasing

| Phase | Scope |
|---|---|
| P0a | Extract the aggregations into plain-signature services; add `resolveZoneForUser`; no new feature |
| P0b | Snapshot assembly, the rule runner, ranking, the cold-start gate, and the first test fixtures |
| P0c | The ten rules, each with tests |
| P0d | Highlights cards on the Insights tab; retire the assistant tab |

P0a changes no behaviour and is worth doing regardless. P0b before P0c on purpose:
the runner, the ranking and the noise controls are the parts that decide whether
this feature is good, and writing ten rules against a runner that cannot rank or
dedupe them produces ten rules that all need rewriting.
