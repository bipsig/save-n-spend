## Repository layout

Save n Spend is a single npm-workspaces monorepo.

| Workspace | Package name | Contents |
|---|---|---|
| `apps/api` | `api` | Express 4 + Mongoose 8 REST service, compiled as CommonJS. |
| `apps/mobile` | `mobile` | Expo SDK 54 / React Native 0.81 iOS app using expo-router. |
| `packages/types` | `@save-n-spend/types` | Domain interfaces shared by both applications. |

`packages/types` is the contract between the two applications. When you change
a domain shape, change it there first — both sides compile against it, so a
mismatch becomes a type error instead of a runtime surprise. See
[Shared types](#shared-types).

**Important**
`apps/mobile/ios/` is generated by `expo prebuild` and is excluded from version
control. Never hand-edit it: the next prebuild discards your changes. Express
native configuration through `app.json` and config plugins instead.

## How a request flows

```
mobile screen
  → lib/<domain>.ts hook           (useBudgets, useGoals, …)
    → lib/query/useApiQuery.ts     (TanStack Query: keys, focus rule, write invalidation)
      → lib/api.ts                 (fetch wrapper; attaches the bearer token)
      → POST /api/v1/<resource>
        → routes/v1/<domain>Routes.ts
          → protect                (JWT verification)
            → controllers/<domain>Controller.ts
              → schemas/<domain>Schema.ts   (Zod validation)
                → models/<Model>.ts         (Mongoose)
                  → utils/response.ts       (envelope)
```

Every route is mounted under `/api/v1`. The router chain is
`server.ts` → `routes/router.ts` (`/v1`) → `routes/v1/index.ts` (per-resource
routers).

Controllers own validation and orchestration. They parse input with the Zod
schema for their resource, act on the model, and reply through a helper from
`utils/response.ts`. Business rules that span more than one document live in
`services/`.

## Money representation

**All monetary amounts are integer paise.** There are no floating-point rupee
values anywhere in the system: not in request bodies, not in Mongoose
documents, not in mobile state.

| Layer | Representation | Example for ₹1,234.50 |
|---|---|---|
| API request and response | integer paise | `123450` |
| MongoDB document | integer paise | `123450` |
| Mobile state and forms | integer paise | `123450` |
| Mobile display | formatted string | `₹1,234.50` |

Convert only at the edges of the mobile app, using `apps/mobile/lib/money.ts`:

| Function | Purpose |
|---|---|
| `formatMoney(paise)` (default export) | Paise to a display string with Indian digit grouping. |
| `parseMoney(text)` | User-entered rupee text to integer paise. |
| `paiseToInput(paise)` | Paise to the plain rupee string a text field expects. |

**Warning**
Never send a rupee float to the API. Every amount field is declared
`z.number().int()`, so a fractional value fails validation with a 400 — and a
value that happens to be integral is silently interpreted as paise, which is
off by a factor of 100.

## The account balance invariant

`Account.balance` is a cached running total. It is only ever modified by the two
functions in `apps/api/src/services/transactionService.ts`.

`getEffectOf(transaction)` maps a transaction to the balance deltas it implies.

| Transaction type | Effect |
|---|---|
| `expense`, `negativeAdjustment` | `account` decreases by `amount`. |
| `income`, `positiveAdjustment` | `account` increases by `amount`. |
| `transfer` | `account` decreases by `amount`; `toAccount` increases by `amount`. |

`applyEffects(transaction, action, session)` applies those deltas with `$inc`.
Pass `"add"` when a transaction comes into existence and `"revert"` when it
leaves. An update is a revert of the old document followed by an add of the new
one.

**Important**
Every call runs inside `session.withTransaction`, so the transaction document
and the balance move together or not at all. If you add a code path that
creates, edits, or deletes a transaction, route it through `applyEffects` inside
a session. Writing to `Account.balance` directly will drift the balance away
from the transaction history, and nothing in the system will detect it.

This is why MongoDB Atlas is a hard requirement rather than a preference:
multi-document transactions need a replica set.

### Correcting a balance without breaking the invariant

Balances drift. A cash purchase never gets recorded, a bank fee arrives that
nobody entered, and the figure in the app stops matching the figure in the bank.
`PATCH /accounts/{id}/balance` is how a user fixes that, and it is built to leave
the invariant intact.

The request body is the **target** balance — the number the user is reading off
their banking app. The controller does not `$set` it:

```
delta = target - account.balance

delta === 0  →  stamp lastSyncedAt, write nothing else
delta > 0    →  positiveAdjustment for  delta,  applyEffects("add")
delta < 0    →  negativeAdjustment for −delta,  applyEffects("add")
```

So the balance still moves only through `applyEffects`, and it is still exactly
the sum of its history — the history simply now contains a row that says "we were
off by this much". The alternative, a direct `$set`, would produce the right
number today and an unexplainable one the moment anything recomputed it.

The adjustment types already existed for this shape of write and are excluded
from income and expense everywhere they are summed, so a correction never shows
up as earnings or spending. They are also hidden from the default transactions
listing: a correction is bookkeeping, and a row in the Activity feed that the
user did not create is a row they cannot explain.

`Account.lastSyncedAt` records when the user last reconciled, and is stamped even
when the balance already matched — "I checked and it was fine" is the answer the
next reconciliation wants, and it is not the same answer as "never checked".

### The one exception

`apps/api/src/scripts/seed.ts` recomputes balances from scratch. It is the only
code allowed to, it refuses to run against a production database, and it is not
a pattern to copy.

## Response envelope

Every response — success or failure — has the same four fields. An error made
by `errorHandler` also carries a fifth, `requestId` (see
[Request references and logs](#request-references-and-logs)).

```json
{
  "success": true,
  "statusCode": 200,
  "message": "Success",
  "data": { }
}
```

| Field | Type | Description |
|---|---|---|
| `success` | boolean | `true` for 2xx, `false` otherwise. |
| `statusCode` | number | Repeats the HTTP status, so a client that only reads the body still knows. |
| `message` | string | Human-readable. On failure this is the text the app shows the user. |
| `data` | any | The payload, or `null` on failure and for deletes. |

Emit the envelope with a helper from `apps/api/src/utils/response.ts` —
`ok`, `created`, `noContent`, `badRequest`, `unauthorized`, `forbidden`,
`notFound`, `conflict`, `serverError` — rather than calling `res.json`
yourself.

On the mobile side, `lib/api.ts` unwraps the envelope and returns `data`
directly, so callers never see the wrapper:

```ts
const budgets = await get<BudgetSummary[]>("/budgets?month=2026-07");
```

**Note**
`noContent` returns HTTP 200 with `data: null`, not HTTP 204. The name follows
the semantics, not the status code.

## Error handling

`apps/api` imports `express-async-errors`, so a rejected promise in an async
handler reaches the error middleware without an explicit `try`/`catch`. Throw
and let it propagate:

```ts
if (!budget) throw AppError.notFound("Budget not found");
```

`AppError` (in `utils/AppError.ts`) carries an HTTP status, the message and an
optional `code` and `issues`, with static constructors for the common cases:
`badRequest`, `unauthorized`, `notFound`, `conflict`, `invalidReference` and
`duplicate`.

`middleware/errorHandler.ts` is the single exit point. Every error leaves in one
shape, `{ success: false, statusCode, code, message, issues?, data: null,
requestId }` (codes and messages: [API reference → Errors](api-reference.md#errors)):

| Error | Status and `code` | Message the client sees |
|---|---|---|
| `AppError` | `err.statusCode`; `err.code`, or one from the status (400 `invalid_input`, 401 `unauthenticated`, or `invalid_credentials` on `/auth/login` and `/auth/change-password`, 404 `not_found`, 409 `conflict`) | `err.message` |
| zod error, v3 or v4 (recognised by `name`) | 400 `invalid_input`, or `invalid_reference` for a bad id from `objectId()` | The first issue's message; every issue in `issues`. Messages come from one error map (`schemas/errorMap.ts`), installed for both zod versions by `schemas/z.ts`. |
| body-parser: broken JSON, bad encoding | 400 `invalid_json` | `The request couldn't be read. Please update the app` |
| body-parser: over 25 MB | 413 `body_too_large` | `That's too big to send` |
| A body sent without `Content-Type: application/json` (`middleware/requireJsonBody.ts`) | 400 `invalid_json` | as broken JSON |
| Mongoose `CastError` on an id in the URL | 404 `not_found` | `That <thing> doesn't exist any more` |
| Mongoose `CastError` on an id in the body or query | 400 `invalid_reference` | `<Label> isn't one of your <things> any more. Pick another` |
| Mongoose `CastError` on another type, `ValidationError` | 400 `invalid_input` (or `invalid_reference` for an id) | A labelled sentence per path, in `issues`. |
| MongoDB duplicate key (`11000`) | 409 `duplicate` | `A record with this value already exists` |
| Unknown route or method (`routeNotFound`) | 404 `route_not_found` | `This part of the app needs an update` |
| Rate limited (`rateLimitHandler`) | 429 `rate_limited`, with `Retry-After` | per limiter |
| Anything else | 500 `internal` | `Something went wrong on our side. Please try again` |

A 401 also carries `WWW-Authenticate: Bearer realm="save-n-spend"`.

**Important**
The 500 branch logs the real error server-side and returns a generic message.
Keep it that way — internal details must not reach the client.

### Validating a route

New and converted routes validate before the handler with `validate({ params,
query, body })` (`middleware/validate.ts`), placed after `protect`, so before
any database read. Schemas import `z` from `schemas/z.ts` (zod's v4 API) and use
the shared fields in `schemas/fields.ts`: `objectId(label, things?)`, `money`,
`positiveMoney`, `calendarDay`, `instant`, `month`, `name(label)`, `timeZone`,
`page`, `limit(max)`. A path failure is a 404; queries drop unknown parameters;
bodies are strict unless the schema is a `z.looseObject` (backup documents); a
missing body is `{}`. Handlers read `req.valid`.

Writes that change more than one document go through `inTransaction(fn)`
(`utils/inTransaction.ts`, built on `mongoose.connection.transaction()`). Load
every document you change inside `fn`, with its session: a document loaded
before the transaction keeps a failed attempt's changes when MongoDB retries.
The connection sets write concern `majority` (`config/db.ts`).

### Request references and logs

`middleware/requestLogger.ts` gives every request a reference. It reuses the
phone's `X-Request-Id` header when that is well formed, otherwise it makes one,
and it returns it in the `X-Request-Id` response header. Every error body made by
`errorHandler` (and the 404 for an unknown route) also carries it as `requestId`,
and `lib/api.ts` appends `· Ref <id>` to the message it throws, so the text a
user sees finds that exact request in the logs.

One row per request, per error reported from the phone
(`POST /diagnostics/client-errors`, open without a token and rate-limited per
IP) and per notification the server tried to raise goes into the `RequestLog`
collection, which expires rows after a week. It stores the route pattern
(`/api/v1/bills/:id`), status, duration, user and error message — never a body
or a query. `GET /diagnostics/requests` returns the user's latest 50 rows for the app's
hidden Diagnostics screen.

## Authentication

Registration and login return a JWT that is valid for 7 days. Every other route
is wrapped in `protect` (`middleware/authMiddleware.ts`), which expects:

```
Authorization: Bearer <token>
```

`protect` verifies the token with `JWT_SECRET` and attaches the payload to
`req.user`. A missing token yields `401 Token is missing`; an invalid or expired
one yields `401 Invalid or expired token`.

`POST /auth/register` and `POST /auth/login` are additionally rate-limited by
`middleware/rateLimiter.ts`. The API sets `trust proxy 1` so the limiter keys
off the real client IP rather than the hosting proxy's.

On the client, the token lives in `store/session.ts`, persisted with
expo-secure-store and hydrated synchronously on boot. `lib/api.ts` reads it per
request, and signs the user out automatically on any 401 outside `/auth/*` —
which is what returns them to the login screen.

### Deactivated accounts

`DELETE /users/me` does not delete anything. It stamps `User.deactivatedAt` and
unsets `pushToken`. Every transaction, budget, bill, goal, account and category
stays exactly as it was, indefinitely.

The reasoning: the overwhelmingly common reason to tap that button is "I'm done
with this app for now", and years of a person's spending history is not
recoverable from anywhere else. Every other `DELETE` in this API already archives
rather than erases, so this makes the account itself consistent with the rest of
it instead of being the one endpoint that behaved differently.

Three places make it coherent, and all three are needed:

| Part | Where | What it does |
|---|---|---|
| The gate | `authController.me` | `GET /auth/me` throws `401` when `deactivatedAt` is set. |
| The undo | `authController.login` | Clears `deactivatedAt` **before** the token is issued. |
| The side effect | `deleteMe` + `reminderJob` | `pushToken` unset; the sweep filters `deactivatedAt: null`. |

**Signing in is the undo.** Correct credentials are proof enough that the person
coming back is the person who left, so there is nothing to confirm — and asking
would mean showing a "your account is deactivated" screen to someone who may not
remember deactivating it.

**Important**
The gate is on `/auth/me` and nowhere else. `protect` verifies the JWT signature
and never reads the database; giving every request a user lookup to catch this
would tax thousands of calls to guard one. `/auth/me` is what the app asks on
launch to decide whether to show the tabs at all, so a `401` there is enough to
put a deactivated account back at the login screen — which is exactly where the
reactivation path starts.

The consequence, accepted knowingly: a token issued before the deactivation can
still reach other endpoints until it expires. That token belongs to the person who
deactivated the account moments earlier on that same device, and the only data it
can reach is their own — which is still sitting there either way.

`{ deactivatedAt: null }` matches both a live account and one written before the
field existed, which is why the reminder job's filter can stay a single equality.

## Period windowing

Screens that show a time window use a signed integer offset, not a date range.

| Offset | Meaning |
|---|---|
| `0` | The current period. |
| `-1` | The previous period. |
| `-n` | `n` periods back. |
| Positive | Not allowed. |

The API enforces this: `insightsQuerySchema` declares
`offset: z.coerce.number().int().max(0).default(0)`. The client enforces the
matching rule in the UI by disabling forward navigation at `offset === 0`
(`canNext={offset < 0}`).

All period math is done in the **user's time zone**, never in UTC and never in
the server's local time. `apps/api/src/utils/monthRange.ts` builds
`{ start, next, label }` from a `YYYY-MM` key through the zone helpers, and
`apps/mobile/lib/budgets.ts` derives its month keys from the same zone. See
[Time zones](#time-zones).

See [Add a period selector](mobile-patterns.md#add-a-period-selector) for the
client-side pattern.

## Time zones

`user.prefs.timeZone` is an IANA zone name and is the **single source of truth**
for every calendar decision either side makes. There is no other clock: the
server does not use its own local time, and the app does not use the device's
zone except to seed the preference at registration.

Two kinds of value are involved, and confusing them is the bug this design
exists to prevent:

| Kind | Example | Stored as |
|---|---|---|
| **Instant** | when a transaction happened | A real UTC timestamp. |
| **Calendar date** | which day a bill is due, which month a budget covers | A day, in the user's zone. |

An instant is absolute. A calendar date only means something once you say whose
zone it is in — "September" starts five and a half hours earlier for a user in
`Asia/Kolkata` than for one in `Europe/London`, and a receipt entered at
00:30 on the 1st belongs to the new month for one and the old month for the other.

### Server

`apps/api/src/utils/timezone.ts` owns the arithmetic. Every helper takes the zone
explicitly — there is no ambient default beyond `DEFAULT_ZONE`, which only
applies when a user has no preference at all.

| Helper | Returns |
|---|---|
| `normalizeZone(zone?)` | A valid zone name, falling back to `DEFAULT_ZONE`. |
| `partsInZone(instant, zone)` | Year, month, day, hour, weekday as seen in that zone. |
| `instantInZone(parts, zone)` | The UTC instant for a zone-local wall-clock time. |
| `startOfDayInZone` / `endOfDayInZone` / `startOfWeekInZone` / `startOfMonthInZone` / `startOfYearInZone` | Window boundaries as UTC instants. |
| `addDaysInZone` / `addMonthsInZone` / `addYearsInZone` | Calendar-correct arithmetic across DST. |
| `monthLabelInZone` / `dayKeyInZone` | `YYYY-MM` and `YYYY-MM-DD` keys. |

`instantInZone` resolves the offset in **two passes**: it guesses using the
offset at a first approximation, then re-reads the offset at the result and
corrects. One pass is wrong for any wall-clock time that falls near a DST
transition, because the offset it needs is the one that applies *after* the
shift.

Request handlers get the zone from `apps/api/src/utils/userZone.ts`:

```ts
const zone = await resolveZone(req);
```

**Important**
Add zone handling by calling `resolveZone(req)` and passing the zone down. Never
call `new Date().getMonth()`, `toISOString().slice(0, 10)`, or any other method
that reads the server's local time or UTC as if it were the user's calendar.

### Mobile

`apps/mobile/lib/zone.ts` mirrors the server, reading the zone from the session
user with the device zone as a fallback. `useAppZone()` subscribes a screen so
changing the setting re-renders every date on it.

Zone changes are made through `PATCH /users/me` only. Registration accepts a
`timeZone` so a new account starts with the device's zone, but after that the
preference is explicit — otherwise flying somewhere would silently re-cut a
user's whole history.

**Note**
`Intl.DateTimeFormat.formatToParts` is used on the server, where Node has full
ICU. On the client it is avoided in favour of arithmetic on offsets, because
Hermes ships a reduced ICU and its part output is not dependable.

## Notifications

Notifications have three moving parts: a stored feed, an optional push, and the
things that raise them.

```
raiser ──▶ notify() ──▶ 1. wantsNotification(prefs, type)   ── no ──▶ stop
                        2. Notification.create(dedupeKey)   ── dup ──▶ stop
                        3. sendPush()                       (best effort)
```

`apps/api/src/services/notificationService.ts` is the only door. The order is
the design:

1. **Preferences first**, so nothing is stored that the user asked not to get.
2. **The write second**, and its `{ userId, dedupeKey }` unique index is what
   makes "once" mean once. Uniqueness is enforced by the database rather than a
   read-then-write check because the reminder job can overlap itself — a slow
   tick, a restart, two instances — and a check-then-write loses that race. The
   second writer gets duplicate key `11000`, which the service reads as "already
   sent".
3. **Push last**, and only when the write was the first one. A retried job
   therefore cannot buzz a phone twice.

**Important**
`notify` never throws. Its callers include a `POST` that has already committed
money, and a failed nudge must not turn a successful write into a 500.

### The in-app feed is the source of truth

Push is a courtesy on top of it. A user who denied permission, or is on a
simulator, or whose project is not yet linked to EAS, still receives every
notification — they open the app to see them. The bell's unread dot and the app
icon badge are both painted from the feed's unread count, so reading something
in-app clears the badge too.

### Dedupe keys

A key names the thing and the occasion, so the same occasion produces the same
key however many times it is evaluated:

| Kind | Key |
|---|---|
| Bill due within lead time | `bill:<id>:due:<dueDayKey>` |
| Bill due today | `bill:<id>:today:<dueDayKey>` |
| Bill overdue | `bill:<id>:overdue:<dueDayKey>` |
| Budget at 80% / over | `budget:<id>:<YYYY-MM>:warn` / `:over` |
| Goal milestone | `goal:<id>:milestone:<25\|50\|75\|100>` |
| Goal deadline near | `goal:<id>:deadline:<deadlineDayKey>` |
| Daily summary | `daily:<dayKeyCovered>` |
| Weekly summary | `weekly:<closingMondayDayKey>` |
| Monthly summary | `monthly:<YYYY-MM>` |
| Revalue investments | `revalue:<YYYY-MM>` |
| New recurring payments found | `recurring:<signature of the suggestions>` |

"Due today" has its own key on purpose: someone reminded three days early should
still hear about it on the morning it is actually due.

### What raises them

**Event-driven** — raised by the request that caused them, after the write commits:

| Raiser | Service |
|---|---|
| Transaction created or updated (expense) | `services/budgetAlertService.ts` |
| Goal contribution | `services/goalAlertService.ts` |

**Cron-driven** — `apps/api/src/jobs/reminderJob.ts`, scheduled hourly and
started from `server.ts` after the database connects:

| Kind | Condition |
|---|---|
| Bill reminder / overdue | Unpaid, unsettled for this period, within the user's lead time. |
| Goal deadline | Deadline 0–7 zone-local days away and the goal is not funded. |
| Recurring found | The recurring-payment detector has expense suggestions that are not bills yet; keyed by the set, so it fires once per new find. |
| Daily summary | Any day, and yesterday had activity. |
| Weekly summary | Monday, and the week had activity. |
| Monthly summary | The 1st, and the month had activity. |
| Revalue investments | The user's chosen day of month (`investmentReminderDay`, default 1), and they hold at least one investment. |

The tick runs hourly in UTC and sends to each user when their **own** zone reads
6 p.m. or later (`partsInZone(now, zone).hour >= SEND_HOUR`, `SEND_HOUR = 18`).
The comparison is `>=` rather than `===` deliberately: a restart or a slow tick
can swallow the 6 o'clock hour entirely, and it is better to send at 8 than not at
all. Sending twice is what the dedupe keys prevent.

### Digest notifications

Three digests, each covering the period that just **closed** — never a rolling
window. A push headed "31 May in review" that includes today's lunch is one the
reader can prove wrong.

| Digest | Period | Hour | Default |
|---|---|---|---|
| Daily | Yesterday, zone-local midnight to midnight | 6pm | off |
| Weekly | Monday to Sunday, closed by this Monday's midnight | 7pm | off |
| Monthly | The previous calendar month | 8pm | **on** |

**Why the evening, and not the morning.** This is a hosting constraint wearing
the costume of a product decision. The API runs on Render's free tier, which
spins the instance down after ~15 minutes idle and then needs 50 seconds or more
to come back. No free uptime pinger will hold a request open that long, so a
pinger can *keep* the service awake but cannot *wake* it — which makes the first
hour of the day the least reliable moment to promise anything, because the day's
first tick only happens once something patient has woken the instance. By 6pm
the service has been up for hours and a tick is as close to certain as this tier
gets. The uptime window runs 7am–11pm local, so 8pm still leaves the monthly
digest three hours of slack to catch up in.

If the API ever moves to a plan without spin-down, the four constants at the top
of `reminderJob.ts` are the only thing to change.

**The stagger is the point.** The 1st of a month can be a Monday, and on that
evening all three periods have just closed at once. Sent together they arrive as
a stack of three pushes that looks like a bug; an hour apart they read as what
they are — yesterday, then the week, then the month. The hours are floors, not
exact times, so a server that was down all day still delivers all three on
the first tick it manages: bunched on the recovery path, which is the right
trade against silence.

Bills, goal deadlines and recurring suggestions share 6pm with the daily digest, because they are about
what is *coming* rather than what happened and so don't compete for the same
attention. An evening bill reminder is arguably better placed than a morning
one, landing when someone is home and able to actually pay it.

**Defaults follow frequency.** Daily and weekly are opt-in; monthly is on. 365
pushes a year is the kind of thing people uninstall an app over and has to be
asked for. Twelve a year, the day the month just ended, is a reasonable
thing for a money app to assume is wanted. This is `wantsNotification` in
`notificationService.ts` — `=== true` for the opt-in kinds, `!== false` for
monthly.

**An empty period sends nothing.** A day with no transactions is the most common
day there is, and a digest of it is the surest way to train someone to swipe
these away unread. All three check `count === 0` and return.

Periods are bounded with `startOfDayInZone` / `startOfWeekInZone` /
`startOfMonthInZone` plus the matching `addDaysInZone` / `addMonthsInZone`, so
February, a 31-day month, and a month containing a DST change all need no special
case — a New York user's March window correctly runs from `-05:00` to `-04:00`.
Dedupe keys name the **period covered**, not the day the job ran, so re-running a
morning is idempotent.

**Important**
Notification copy is composed on the server, where no app is running to format
money — hence `apps/api/src/utils/money.ts`. The figures a notification quotes
come from the same services the screens use (`budgetService`, `billService`),
so an alert can never disagree with the page it opens.

### Retention

A TTL index expires notifications 90 days after creation. This is also what
re-arms the dedupe keys, which is wanted: a yearly bill's reminder should be
allowed to fire again next year.

## Health score

`apps/api/src/services/healthService.ts` produces the one number on the dashboard
that is a **judgement** rather than a fact. Everything else on that screen is
arithmetic the user could redo by hand; this is the app's opinion of them. That
raises the bar, because the first time the score moves for a reason the user
cannot see, they stop trusting the rest of the screen too.

Four rules follow from that, and they are the design:

1. **Every point is attributable.** The total is a weighted average of five
   pillars, each reporting its own measurement, verdict and next action. `62` is
   never the answer; "62, because your buffer is thin" is.
2. **A pillar that does not apply is not scored.** It returns `score: null` and
   the remaining pillars share the weight.
3. **It refuses to guess.** Under 30 days of transaction history there is no
   score at all — `score: null` plus a `reason`.
4. **It measures 90 days, not this month.**

### The five pillars

| Pillar | Weight | Measures | Curve anchors (measurement → points) |
|---|---|---|---|
| Savings rate | 30 | `(income − expenses) / income` over the window | 0% → 0, 5% → 25, 20% → 80, 30% → 100 |
| Safety buffer | 25 | `(liquid − card debt) / monthly expenses`, in months | 0 → 0, 1 → 40, 3 → 75, 6 → 100 |
| Bills | 20 | Share overdue now, minus a staleness penalty | `100 × (1 − overdue/total) − min(30, worst days late)` |
| Budgets | 15 | Spend against **pace**, weighted by limit | 1.0× → 100, 1.5× → 0 |
| Goals | 10 | Contribution rate ÷ required rate, weighted by target | linear, clamped to 100 |

Weights are ordered by how much each predicts about someone's finances a year
out. Savings rate leads because what you keep out of what you earn determines
everything downstream. Buffer is next because it is what makes the other three
survivable. Bills, budgets and goals descend from obligation to self-set target
to discretionary: missing a budget you set ambitiously is not the same failure
as spending more than you earn, and someone with no goals and a 30% savings rate
is not unhealthy.

Scores come from a table of anchors interpolated linearly (`curve()`), not from
nested ternaries, so every judgement call is visible and arguable. All the tables
are steeper at the bottom than the top: going from saving nothing to saving 5% is
a real change in someone's life, going from 30% to 35% is a rounding error, and a
straight line would rate them the same.

### Rules that make the number honest

**Renormalisation, not zeros.** The total divides by the weight of the
*applicable* pillars. Docking someone 15 points for never opening the budgets
screen would make the score a measure of feature adoption. The accepted
trade-off: deleting a budget you are overspending removes its penalty. Nobody
games their own mirror, and the two pillars carrying 55% between them — savings
and buffer — are computed from money that has already moved and cannot be dodged
by deleting anything.

**The critical ceiling.** If any applicable pillar scores below 25, the total is
capped at 79 — the top of "Good". A weighted average will happily let a strong
savings rate and a fat buffer carry the headline to "Excellent" while five bills
sit a month overdue. The average is arithmetically right and the word is wrong,
and the word is what the user reads first.

**Pace, not month-end.** On the 5th everybody is under budget. Budgets are scored
against `limit × (days elapsed / days in month)`, floored at seven days so day 1
does not judge a weekly grocery run against a single day's allowance.

**Rate, not completion, for goals.** Only goals *with a deadline* are scored — a
goal with no date is an aspiration, and grading it would punish someone for
writing down something they want. For the rest, what has gone in per month since
creation is compared against what is now needed per month. A goal created
yesterday at 0% is not failing; one that needed ₹8,000 a month and has been
getting ₹3,000 is, and no completion percentage would say so.

**Transfers and adjustments are excluded** from income and expenses — moving
money between your own accounts is not earning or spending, and a balance
correction is bookkeeping. Both still move `Account.balance`, so they reach the
buffer pillar, which is where they belong.

**What is measured only in the present.** The bills pillar can only see what is
overdue *right now*. That is a data limitation, not a choice: a recurring bill is
never marked paid, its due date rolls forward, so once this month's electricity
is settled there is no record of whether it was settled late.

### Why 90 days

One calendar month is the wrong window for a verdict: a salary landing on the 1st
instead of the 31st, an annual insurance premium, or one laptop swings a monthly
savings rate by tens of points, and a score that jumps 30 points for a reason the
user considers normal is a score they learn to ignore. A year is the opposite
failure — so slow to move that someone who fixes their spending sees no reward
for months and concludes the number is fake. 90 days absorbs one irregular month
while still responding to a real change in habits within a few weeks.

### Client responsibilities

None, arithmetically. `apps/mobile/lib/health.ts` holds only presentation — band
colours, pillar icons, and the fetch. A judgement computed in two places is two
judgements, and the client's job is to not disagree with the server.

> **Important**
> Green is used only for the top two bands. A card glowing green at 55/100 tells
> the user they are fine while the number says they are not, and colour is what
> people read before text. Pillar rows are coloured by their **own** score, not
> the total, so one weak pillar under a healthy total is findable at a glance.

## Trips

A trip is a stretch of dates, the people on it and an optional budget. Everything
spent on it is **ordinary transactions** tagged with the trip's id, so balances,
cash flow and totals stay true without a second ledger. The trip layer decides
what those transactions are and which screens read them.

### Models

| Model | Holds |
|---|---|
| `Trip` | `name`, `emoji`, `color`, `startDate`, `endDate`, `members` (person account ids, not including you), `budget` (paise or `null`), `status` (`active` / `closed`), `closedAt`, and the optional `plan` (see [Matching Splitwise](#matching-splitwises-simplified-debts)). |
| `TripExpense` | One shared expense as the group sees it: `title`, `occurredAt`, `category`, `cost` (the whole bill), `paidBy` (`null` = you, else a member's person account), `paidFrom` (your account, when you paid), `shares` (`{ account \| null, amount }`, `null` = you), `source` (`manual` / `splitwise`) and `importKey`. |
| `Transaction` | Two optional fields: `tripId` on **every** row a trip created or settled, and `tripExpenseId` only on the rows a trip expense generated. |

A `TripExpense` is never summed as spending. It generates transactions, and the
transactions are what every total reads. `TripExpense.cost` is read for exactly
two figures, `totals.paid` and `totals.wholeTrip`.

Dates on a trip are calendar days stored as UTC midnight; the mobile app crosses
to the date picker with `tripDayToPicker` / `pickerToTripDay`.

### The rule: your spending is your share

`services/tripLedger.ts` is pure (tested in `tripLedger.test.ts`) and holds the
rule the feature rests on, whoever paid:

| What happened | Transactions written |
|---|---|
| You paid ₹4,000, split four ways | An `expense` of ₹1,000 from your account, plus a `transfer` of ₹1,000 to each friend's person account. |
| A friend paid ₹2,000, split four ways | An `expense` of ₹500 charged to the friend's person account. Your share is the spending; their balance going negative means you owe them. |
| Anyone settles | A `transfer` between you and them. Never spending or income. |

A person account (`Account.type = "person"`) is a receivable: its balance is what
that person owes you, negative when you owe them. A member's trip balance is
exactly what the trip's transactions did to their person account
(`memberBalances`).

`services/tripService.ts` writes the rows inside one `session.withTransaction`,
through `applyEffects`, so [the balance invariant](#the-account-balance-invariant)
holds. Editing an expense reverts and deletes its rows and writes the new ones
together; deleting a trip reverts every row it owns, so balances end as if it was
never logged. A closed trip refuses expense changes; **settle-ups, plans and
deletion are still allowed on a closed trip**.

Transactions with a `tripExpenseId` cannot be changed from the Transactions API:
`updateTransaction`, `deleteTransaction` and `convertToInvestment` answer `400
This is part of a trip expense — change it from the trip`.

Importing, planning and closing are the other writers:

| Service | Does |
|---|---|
| `splitwiseCsv.ts` | Reads a Splitwise group export (one row per expense, a column per person; "Payment" rows are settle-ups; a "Total balance" row). Pure, tested against a real file. |
| `tripImportService.ts` | `previewImport` saves nothing: it maps names to you or a person account, sorts each row (`ready`, `matchesYours`, `pickAccount`, `lump`, `settlement`, `isThisYours`, `alreadyIn`, `skipped`) and suggests a category. `commitImport` applies only what was approved, as trip expenses and settle-ups fingerprinted with the row's key, so importing the file again adds only new rows. Live trips only. It also answers `matchSplitwise`, whether Splitwise's simplification could have changed anyone's amount. |
| `closeTrip` | Always allowed. Each leftover balance is either kept on the person account or *let go* (`planLetGo`): an amount they owed becomes an expense charged to them, an amount you owed becomes a `positiveAdjustment`. `reopenTrip` undoes the lock only. |

Routes are under `/trips` (`routes/v1/tripRoutes.ts`): list, create, detail,
patch, delete; `POST /:id/expenses`, `PATCH`/`DELETE /:id/expenses/:expenseId`;
`POST /:id/settle`; `PUT`/`DELETE /:id/plan`; `POST /:id/close` and `/reopen`;
`POST /:id/import/preview` and `/import/commit`. Request shapes are in
[the API reference](api-reference.md).

### Matching Splitwise's simplified debts

With "simplify debts" on, Splitwise re-routes who pays whom, so a person's exact
balance can differ from what they will actually pay. A trip's `plan` stores the
second set of numbers, typed in from Splitwise, as paired balance adjustments on
the person accounts. They net to zero, so your bank and net worth never move.

- The adjustments are `positiveAdjustment` / `negativeAdjustment` rows with the
  note `Matched to Splitwise` and a `clientId` of **`plan:<tripId>:<personAccountId>`**
  (`rerouteKey`). `isReroute()` recognises them by that prefix.
- Saving a plan removes the earlier `plan:` rows first and writes the new ones, so
  saving again replaces rather than stacks. `DELETE /:id/plan` removes them and
  unsets `trip.plan`.
- `validatePlan` requires the entered amounts to add up to what you are owed
  overall; anyone left out pays nothing.
- `plan.signature` is a hash of the trip's expenses (`expensesSignature`). The
  detail payload's `plan.stale` is true once expenses are added, removed or
  changed. Settle-ups are not part of the signature, because they move the exact
  and the planned balance by the same amount.
- The detail payload reports, per member, `balance` (with the plan), `exact`
  (without) and `routed` (the difference). `plan:` rows and `exact` are left out
  of the journal: they are bookkeeping, not events on the trip.

### Where trip rows are counted

**2.8.6: the trips rule.** The 2.8.6 app reads every total with `trips=entries`
(see [API reference → Trips rule](api-reference.md#trips-rule-286-tripsentries)): a closed
trip is one expense in the built-in category Trips (`"trips"`, not a Category id) on its
close day `Trip.closedOn`, with your whole share; open trips count nowhere; none of a trip's
own rows count outside the trip page. One aggregation stage does this for every read,
`entryStages` in `services/tripEntries.ts`: everyday rows plus a `$unionWith` that builds one
synthetic expense row per closed trip, dated at the end of its close day in the user's zone.
`closedOn` is set when the trip is closed (default: its last expense day), changed with
`PATCH /trips/:id/close-date`, cleared on reopen, and read from `closedAt` in the user's zone
for trips closed before 2.8.6. Budgets, Safe to spend, recurring, Quick Log suggestions,
category insights' own figures, cash flow and streaks stay as below. The Health buffer stays
on everyday spending. The server's digests follow the rule for everyone.

The table below is the meaning **without** `trips=entries`, which the 2.8.5 app still gets
unchanged. Trip rows are real money and always move balances and net worth; the difference
is whether a screen's *spending* figures include them.

| Surface | Trip rows |

| `GET /transactions/title-suggestions` (Quick Log) | Left out. |

## Investments

A holding is an `Account` of `type: "investment"`. Nothing needs market data;
every figure is typed in by the user.

| Event | Stored as |
|---|---|
| Putting money in (a contribution or SIP) | A `transfer` **into** the holding. |
| Taking money out (a redemption) | A `transfer` **out** of it. |
| Updating what it is worth | A `positiveAdjustment` / `negativeAdjustment` on the holding (the balance-sync path). |

So, per holding, `invested = startingBalance + Σ transfers in − Σ transfers out`,
`current` is the stored balance, and `gain = current − invested` (the sum of its
adjustments, plus any opening gain). `startingBalance` is the cost basis when the
holding was added; `investedSince` and `investedHow` (`sip` / `lump`) date it so
the yearly return can be worked out (`services/investmentMath.ts`). Investment
accounts are left out of the "paid from" pickers (Add Transaction, Mark paid, the
default account), and person accounts too wherever the money has to be real.

`GET /investments` returns the hub: holdings, totals, allocation by kind and
this month's contributions. `GET /investments/:id/history` is one holding's last
200 transactions, including the adjustments Activity hides.

### Month-end history is derived, never stored

`GET /investments/trend` and `GET /investments/report` read the transfers and
value updates that already exist and compute each holding's history on the spot
(`services/investmentHistoryMath.ts`, pure, `investmentHistoryMath.test.ts`).
**Nothing is stored for history**, so editing or deleting a past entry corrects
the history with it.

```
invested(t) = startingBalance + money in − money out, up to t
gain(t)     = opening gain + every value update, up to t
value(t)    = invested(t) + gain(t)
```

- **Opening gain recovery.** The value typed when the holding was added is not
  saved as an entry of its own. It is recovered as whatever today's balance has
  that the dated records do not explain: `balance − startingBalance − flows − updates`.
- **Carry-forward.** A month with no value update keeps the last known gain. Money
  added since counts at cost, and nothing is assumed to have grown or fallen. Such
  a month is flagged `upd: false`.
- **Growth is the change in gain**, not the change in value:
  `(value − invested)` this month minus last month's. Money added is not growth.
  `pct` is growth over last month's value plus this month's contributions. The
  first month has no growth (`opening: true`). `cover` is how many months one
  update spans.
- **Where it starts.** The first month is the earliest of the holding's creation,
  first transfer and first update, in the user's zone. Nothing earlier is drawn.
- **The current month is partial.** Its point takes everything on record, so it
  equals today's balance (`partial: true`).
- **Portfolio.** Starts at the earliest holding. A holding contributes only from
  its own first month, and growth sums only holdings that already existed last
  month; one added this month has an opening value, not growth.
- **Ledger.** `holdingLedger` lists every entry (`added`, `in`, `out`, `update`)
  oldest first with the value each left the holding at. `/investments/report`
  returns the hub's figures, the trend and the whole ledger in one read.

## Cold-start gate

The API runs on Render's free tier, which suspends an idle instance and takes
roughly 35 seconds to wake it. Without a gate, the first launch after an idle
period shows error states on every screen while the instance boots — which reads
as a broken app rather than a sleeping one.

`apps/mobile/store/wake.ts` polls the unauthenticated `GET /health` before the
app is allowed to render, and `components/shell/WakeGate.tsx` holds a waking
screen in front of the router until it answers.

| Phase | Meaning | What the user sees |
|---|---|---|
| `probing` | First attempt in flight (2.5s ceiling). Launch-only | Nothing — the splash is still up |
| `waking` | First attempt did not answer; retrying (8s each, 60s budget) | The waking screen |
| `awake` | Server answered | The app |
| `unreachable` | Budget spent | "Can't reach the server" + Try again / Continue anyway |

Notes on the design:

- **`/health`, not `/dashboard/health`.** The probe must be cheap, tokenless and
  meaningful before login. The liveness endpoint touches no database. The two are
  unrelated despite the names — one is the server's pulse, the other is the
  user's.
- **The worst bug it fixes is not the wait.** Boot used to call `/auth/me` as its
  first request, so a cold start timed out and threw away a perfectly good token:
  the user read "the server was asleep" as "the app logged me out". `_layout`
  now awaits the probe before `/auth/me`, and the boot flow discards a token only
  when the server **answered** and refused it — a `401` or `403`. Everything else
  buys one more attempt behind a fresh probe. That is what `ApiError.status === 0`
  in `lib/api.ts` is for: a request that never landed says nothing about whether
  the token is good, and the two must not be the same value to a caller.
- **Nothing renders for a warm server.** The first attempt gets a short ceiling
  and paints nothing, so a server answering in 300ms is never made to look slow
  by a spinner that flickers past. The splash covers that window.
- **It can always be escaped.** Past ~40 s the waking screen offers "Continue
  anyway"; a failed probe insists on it. Not sooner: a measured cold start is
  ~33 s, and an exit offered while the expected wait is still running invites
  people to bail out just before it would have worked. A gate with no way out is
  a worse bug than the cold start it was hiding.
- **It runs once per launch, not per request.** Once the instance is awake it
  stays awake for as long as it is used, so re-probing per screen would spend
  requests to learn something already known.

A re-probe (`retry()`) goes straight to `waking`, never back to `probing`: by then
the server is known to be unresponsive, so there is no warm case left to optimise
for, and `probing` paints nothing — which would blank a screen the user is
already looking at.

> **Important**
> `WakeGate` renders *in place of* the `Stack`, so until it opens there is no
> navigator. The auth-routing effect in `app/_layout.tsx` is gated on
> `phase === "awake"` for that reason: `hydrate()` can settle to `guest` while
> the server is still waking, and a `router.replace()` at that moment fires
> before the root layout has mounted.

### App Lock and the two halves of boot

`AppLockGate` renders the lock as an **overlay over** the `Stack`, not in place of
it — unlocking has to put the user back on the screen they left, and a navigation
swap would drop them on the home tab.

Coming up locked on a cold start needs **both** halves of boot to have resolved,
and this is where it went wrong. The effect was keyed on `hydrated` alone, which
is the settings store returning from AsyncStorage — a local read that always beats
`/auth/me` over the network. So it fired while `status` was still `"loading"`, the
`status === "authed"` condition failed, and nothing ever re-ran it. **App Lock
worked on every return from the background and never once on a cold start.**

Adding `status` to the deps is the naive fix and is also wrong: a fresh login is
another transition into `"authed"`, so the app would lock the instant someone
signed in. A `armedAtBoot` ref separates the two — the cold-start decision is made
exactly once per launch, and by the time anyone reaches the login screen boot has
already resolved to `"guest"` and the decision is spent.

That ref is also what preserves the original intent, now that `appLock` is in the
deps: switching the toggle on from Settings must not lock the screen the user is
standing on.

| `PORT` | No | Listening port. Defaults to `3000`. Local development uses `7019`. |
| `HOST` | No | Interface to bind. Defaults to `127.0.0.1` outside production, so a dev API holding the dev database is reachable only from the machine it runs on; defaults to `0.0.0.0` when `NODE_ENV=production` or Render's `RENDER` variable is set. `HOST=0.0.0.0` opts a dev server out, to reach it from a phone on the LAN. |
| `DB_USERNAME` | Yes | Atlas cluster user. |
| `DB_PASSWORD` | Yes | Atlas cluster password. |
| `JWT_SECRET` | Yes | Signing secret. `protect` throws at request time if it is unset. |
| `SALT_ROUNDS` | No | bcrypt cost factor. `10` locally. |
| `NODE_ENV` | No | `production` selects the production database. Anything else selects dev. |
| `DB_NAME` | No | Overrides the resolved database name — for a throwaway test database. |
| `DISABLE_REMINDERS` | No | `true` stops `startReminderJob` from scheduling. Set it on any instance that shares a database with another one, and locally, so a dev run cannot notify real users. |
| `EXPO_ACCESS_TOKEN` | No | Required only once push security is enabled in the Expo project. Without it the SDK sends unauthenticated, which works until then. |

There is no `MONGO_URI`. `config/db.ts` assembles the connection string from
`DB_USERNAME` and `DB_PASSWORD` against a fixed cluster host, then selects the
database with mongoose's `dbName` option:

| `NODE_ENV` | Database |
|---|---|
| `production` | `save-n-spend-prod` |
| anything else | `save-n-spend-dev` |

**Important**
Because a dev API listens on loopback, the app has to reach it as `localhost`:
run Metro with `npm start -- --localhost` (or start the API with
`HOST=0.0.0.0`). [Shipping](SHIPPING.md) covers the two options and the
simulator workflow, so they are not repeated here.

**Important**
The database is chosen by `NODE_ENV`, not by a separate connection string, and
both databases live on the same cluster. Setting `NODE_ENV=production` in a local
`.env` therefore points your development machine at production data. Leave it
`development` unless you mean it.

### Mobile environment variables

Only `EXPO_PUBLIC_*` variables are visible to app code.

| Variable | Description |
|---|---|
| `EXPO_PUBLIC_API_URL` | Full API base, including `/api/v1`. When unset, `lib/api.ts` derives the Metro host and appends `:7019/api/v1`. |

`apps/mobile/.env.production` is committed deliberately. Expo inlines
`EXPO_PUBLIC_*` into the JavaScript bundle at build time, so these values are
readable by anyone with the binary and must never hold a secret.

**Important**
Because the value is inlined at build time, editing `.env.production` has no
effect until you rebuild. The `npm run ipa` script prints the baked API URL at
the end of a build so you can confirm what the binary will actually call.

## Known issues

Things that are wrong today and confirmed in the code. They are tracked as open
work in the repository's `to-do.md`, under "Consistency audit".

### Schemas are split across two zod entry points

The root `package.json` pins `zod` to 3.25.76, which ships both the v3 API
(`import z from "zod"`) and the v4 API (`import z from "zod/v4"`). Backup,
dashboard, notification and transaction schemas use v4; the rest use v3. Both
are now recognised by the error handler and share one error map, so neither
answers 500 for bad input any more. New and converted schemas import `z` from
`schemas/z.ts` (v4); the v3 files move over as each area is converted.

### Trip rows are treated differently by different surfaces

The table in [Where trip rows are counted](#where-trip-rows-are-counted) is the
whole picture. The disagreements it shows:

- **"Spent this month" on Home and Activity.** Home reads `/dashboard/summary`,
  which counts trip rows; Activity's summary leaves them out of `expenses`.
- **Review's biggest expense.** The headline leaves trip rows out; the timeline
  moment counts them.
- **Category share of spend.** `GET /insights/category/:id` takes trips out of
  the category's total but divides by every expense, trips included, and the
  breakdown's own total includes the `Trips` slice.
- **The Activity export** leaves trip rows out, matching the screen, so the file
  does not reconcile to the account ledger. Whether it should is an open product
  decision.

### Other

- `GET /transactions` hides balance adjustments by default, and the exports use
  that default, so exports do not contain them even though a comment in
  `transactionController.filterTransactions` says they do.
- The dashboard's net-worth history (`services/netWorthHistoryService.ts`) walks
  back from today's total over the same accounts (non-archived ones): each row
  counts only where it lands on one of them, transfer legs included (D24, 2.8.4).
  Up to 2.8.3 it used every account's income, expenses and adjustments and
  ignored transfers, so archiving an account moved every past point.
